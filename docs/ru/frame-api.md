# API рамки, используемый Divoom Times Frame Sync

[English](../en/frame-api.md) | **Русский**

Этот справочник описывает все сетевые операции из [frame.py](../../src/timesframesync/frame.py) и порядок их использования в [sync.py](../../src/timesframesync/sync.py). Он основан на коде проекта и проверках на конкретной Times Frame от 26 сентября 2026 года. Это описание наблюдаемого поведения прошивки, а не официальная спецификация для всех устройств Divoom. Версия исследованного бинарника и детали исследования приведены в [protocol.md](protocol.md).

## Список методов

| Операция | HTTP | Метод клиента | Назначение |
| --- | --- | --- | --- |
| `Channel/GetConfig` | `POST /divoom_api` | `info()` | Общая конфигурация экрана |
| `Channel/GetClockInfo` | `POST /divoom_api` | `check_available()`, `info()`, `play_album()` | ID устройства и активного альбома/циферблата |
| `Photo/LocalAddToAlbum` | `POST /upload` | `import_photo()`, `import_video()` | Загрузить фото или видео в штатный альбом |
| `Photo/DevicePhotoToAlbum` | `POST /upload` | `add_existing()` | Добавить существующее фото в альбом |
| `Photo/RemovePhotoFromAlbum` | `POST /upload` | `remove_from_album()` | Исключить фото из одного альбома |
| `Device/ExitCustomControlMode` | `POST /divoom_api` | `restore()` | Выйти из внешнего управления экраном |
| `Channel/SetClockSelectId` | `POST /divoom_api` | `select_clock()` | Выбрать штатный альбом/циферблат |
| `Device/GetScreenSnapshot` | `POST /divoom_api` | `snapshot()` | Создать снимок экрана |
| Чтение базы фото | `GET /userdata/pic_db.bin` | `inventory()` | Найти альбом, фотографии и связи между ними |
| Чтение файла | `GET /userdata/<path>` | `fetch_file()`, `file_digest()` | Проверить файлы медиа или скачать снимок экрана |

## Общий транспорт и формат

Базовый адрес: `http://<DIVOOM_HOST>:<DIVOOM_PORT>`, порт по умолчанию — `9000`. Клиент использует отдельную `requests.Session` с `trust_env=False`, поэтому запросы к рамке не идут через прокси из окружения.

### Оболочка команды

`Frame.metadata()` формирует JSON:

```json
{
  "Command": "Channel/GetClockInfo",
  "ReturnCode": 0,
  "DeviceToken": 123456,
  "LocalToken": 123456
}
```

| Поле | Тип | Как заполняется |
| --- | --- | --- |
| `Command` | string | Точное имя команды, с учётом регистра |
| `ReturnCode` | integer | Всегда `0` во входном сообщении: такой формат принимает исследованный обработчик |
| `DeviceToken` | integer | Значение `DIVOOM_TOKEN`, если оно задано |
| `LocalToken` | integer | То же значение `DIVOOM_TOKEN` |

Числа в примерах вымышлены. Ниже токены для краткости опущены; клиент добавляет их ко всем POST-командам через общую оболочку. GET файлов отправляется без JSON и без токенов в query string, как при проверках на устройстве. Необходимость каждого из двух полей токена по отдельности не исследовалась.

### `/divoom_api`

Тело — компактный JSON, `Content-Type: application/json`. Этот путь используется для чтения состояния, выбора экрана и создания снимка.

### `/upload`

Тело — `multipart/form-data; boundary=<случайная граница>`. Первая часть всегда содержит JSON, вторая, если требуется, — файл. Для видео третья часть содержит обложку WebP; у обеих файловых частей `name="file"`. Заголовки частей:

```text
--<boundary>\r\n
Content-Disposition: form-data; name="json"; filename="cmd.json"\r\n
Content-Type: application/json\r\n
Content-Length: <число байтов JSON>\r\n
\r\n
<JSON>\r\n
--<boundary>\r\n
Content-Disposition: form-data; name="file"; filename="im-<24 hex>.webp"\r\n
Content-Type: application/octet-stream\r\n
Content-Length: <число байтов файла>\r\n
\r\n
<байты WebP>\r\n
--<boundary>--\r\n
```

В этой схеме `\r\n` обозначает настоящие байты CRLF. `Content-Length` нужен **в каждой части**, помимо общей длины HTTP-тела, которую выставляет `requests`. Для команд изменения состава альбома часть `file` отсутствует: после JSON следует закрывающая граница. Для фотографий и JSON-only команд используется `multipart()`, для видео — `FileMultipart`. Последний вычисляет общую длину заранее и читает файлы частями до 1 МиБ: HTTP chunked encoding не используется. Файлы закрываются и при успешной отправке, и при исключении.

На исследованной прошивке `Photo/*` через `/divoom_api` могли подтверждаться без выполнения. Через `/upload` эти сообщения поступают в общую очередь команд и выполняются. Поэтому замена endpoint для фото-команд нарушает синхронизацию.

### Ответы, ошибки и повторные попытки

Типичный ответ команды управления экраном, сокращённый:

```json
{
  "Command": "Channel/GetClockInfo",
  "DeviceId": 123000001,
  "PacketFlag": 1700000000,
  "DeviceType": "Frame",
  "ReturnCode": 0,
  "ReturnMessage": ""
}
```

`DeviceId` — числовой идентификатор устройства. `PacketFlag` сохраняется как непрозрачное поле прошивки; клиент не использует его для проверки выполнения. После `/upload` ответ обычно короче:

```json
{"ReturnCode": 0, "ReturnMessage": ""}
```

`_post()` проверяет HTTP-статус, разбирает JSON и требует `ReturnCode == 0`. Пример наблюдавшейся ошибки: `ReturnCode: 1`, `ReturnMessage: "command timeout"`. Значения остальных кодов не установлены; любой ненулевой или отсутствующий код считается ошибкой.

Перед опросом источников `check_available()` отправляет один `Channel/GetClockInfo` с таймаутами соединения/чтения `(3, 3)` секунды. Проверка не читает базу, не переключает альбом и не повторяет запрос внутри себя. Ошибки соединения, таймауты и обрыв тела ответа вызывают `FrameUnavailable` — подкласс `SyncError`; отказ API, ошибки HTTP и JSON остаются обычными `SyncError`. Цикл обрабатывает недоступность без дублирования вложенных ERROR-сообщений.

Таймауты соединения/чтения по умолчанию — `(5, 60)` секунд. Для отправки видео — `(5, 300)`, для потокового чтения файлов — `(5, 90)`. Это таймауты сетевых операций, а не общий предел длительности синхронизации. Автоматического повтора POST нет: неопределённый результат импорта сначала нужно сверить с базой, иначе можно получить дубликат. `run` повторяет весь цикл после `SYNC_INTERVAL`, `sync` возвращает ошибку.

Успешный ACK означает только принятие сообщения. Для фото-команд результат дополнительно проверяется по базе и файлу; для выбора альбома — по `Channel/GetClockInfo`.

## 1. `Channel/GetConfig`

**HTTP:** `POST /divoom_api`. **Использование:** `Frame.info()`; команды `status`, `sync --dry-run`, а также чтение состояния перед синхронизацией.

Запрос без дополнительных параметров:

```json
{"Command": "Channel/GetConfig", "ReturnCode": 0}
```

В ответе присутствует общая оболочка и могут быть `RotationFlag`, `ClockTime`, `GalleryTime`, `SingleGalleyTime`, `ChannelIndex`, `StartUpClockId`, `GalleryShowTimeFlag`. `info()` возвращает ответ целиком в ключе `config`. Программа не интерпретирует перечисленные настройки и не меняет их; полный смысл их значений в этом проекте не установлен.

Это операция чтения. Успех проверяется общей проверкой HTTP/JSON/`ReturnCode`. Повторное чтение не меняет альбом или выбранный экран. При ошибке `info()` не возвращает частично заполненный результат.

## 2. `Channel/GetClockInfo`

**HTTP:** `POST /divoom_api`. **Использование:** `Frame.check_available()`, `Frame.info()`, проверка `Frame.play_album()`.

Запрос:

```json
{"Command": "Channel/GetClockInfo", "ReturnCode": 0}
```

Пример сокращённого ответа:

```json
{
  "Command": "Channel/GetClockInfo",
  "ReturnCode": 0,
  "DeviceId": 123000001,
  "DeviceType": "Frame",
  "Brightness": 100,
  "ClockId": 123456
}
```

| Поле ответа | Использование |
| --- | --- |
| `DeviceId` | В синхронизаторе должен быть integer; вместе с ID обоих альбомов ограничивает область действия локального журнала |
| `ClockId` | ID активного циферблата **или штатного фотоальбома**; сохраняется для `restore` и проверяется после выбора альбома |
| `Brightness` | Передаётся в диагностический вывод без изменений |

Чтение не переключает экран. `play_album()` требует совпадения возвращённого `ClockId` с ID целевого альбома. Отсутствие ожидаемого ID или другой ID после переключения приводит к ошибке, даже если ACK был успешным.

## 3. `Photo/LocalAddToAlbum`

**HTTP:** `POST /upload`, JSON и файл (для видео ещё обложка). **Использование:** `Frame.import_photo()` / `Frame.import_video()`, когда в базе нет файла с ожидаемым коротким именем.

Пример JSON-части:

```json
{
  "Command": "Photo/LocalAddToAlbum",
  "ReturnCode": 0,
  "ClockId": 123456,
  "ParentClockId": 0,
  "ParentItemId": 0,
  "UserId": 0,
  "SendTime": 1700000000000,
  "TakingTime": 1700000000000,
  "PhotoX": 0,
  "PhotoY": 0,
  "PhotoWidth": 800,
  "PhotoHeight": 1280,
  "PhotoIndex": 0,
  "PhotoTotalCnt": 1,
  "PhotoFlag": 123456789,
  "FileName": "im-0123456789abcdef01234567.webp",
  "PreviewFileName": "",
  "PhotoTitle": ""
}
```

| Поле | Тип | Значение, отправляемое клиентом |
| --- | --- | --- |
| `ClockId` | integer | ID существующего обычного альбома из `album_head` |
| `ParentClockId`, `ParentItemId` | integer | `0`; вложенные элементы циферблатов не используются |
| `UserId` | integer | `DIVOOM_USER_ID`; если не указан, `0` — локальный отправитель |
| `SendTime` | integer | Текущее Unix time в миллисекундах |
| `TakingTime` | integer | То же текущее время; дата съёмки из исходного сервиса пока не переносится |
| `PhotoX`, `PhotoY` | integer | `0`, `0` |
| `PhotoWidth`, `PhotoHeight` | integer | `800`, `1280`, размер подготовленного изображения |
| `PhotoIndex`, `PhotoTotalCnt` | integer | `0`, `1`; один файл на операцию |
| `PhotoFlag` | integer | Случайное число от `0` до `2^31 - 2`, идентификатор партии |
| `FileName` | string | Только имя файла; совпадает с `filename` второй multipart-части |
| `PreviewFileName` | string | Для фото пустая строка; для видео имя WebP из третьей части |
| `PhotoTitle` | string | Пустая строка: подписи не переносятся |

`device_photo()` кодирует отдельный RGB WebP с `quality=90`, `method=4`. Имя: `im-` + первые 24 hex-символа SHA-256 **от отправляемых WebP-байтов** + `.webp`, всего 32 ASCII-байта. Подготовка под 800×1280 выполняется во временном файле перед загрузкой. После подтверждения фото и записи журнала временный файл удаляется; контрольные суммы сохраняются. Одинаковые байты дают одинаковое имя и позволяют переиспользовать фото.

`multipart()` разрешает имена длиной не больше 32 символов из `a-z`, `0-9`, `-`, `_`, `.`. Длинные имена опасны для этой прошивки: команда копирования обложки использует 128-байтный буфер; при исследовании длинный путь вызывал перезапуск приложения рамки. Путь вместо имени, пробелы и произвольные символы не отправляются.

Побочные эффекты: приём файла в `/userdata/app_pic/`, перемещение в каталог года/месяца, регистрация в `pic_info`, создание связи в `album_pic`, служебная обработка превью/обложки. Итоговый путь берётся из базы, а не вычисляется на компьютере.

**Проверка:** после ACK клиент опрашивает базу с паузой 0,5 с, ожидая запись с таким именем. Окно ожидания — 15 с, без учёта возможного превышения из-за сетевых таймаутов. Затем скачивает файл и сравнивает байты. Если запись есть, но членство в альбоме отсутствует, вызывает `Photo/DevicePhotoToAlbum`. При отсутствии записи, несовпадении байтов или неуспешном добавлении в альбом возвращается ошибка.

**Повтор:** импорт сам по себе не считается идемпотентным. Следующий цикл сначала ищет запись по имени и проверяет байты. Найденный файл переиспользуется; при нескольких записях с одинаковым именем синхронизация останавливается для устранения неоднозначности.

### Импорт видео той же командой

`Frame.import_video()` отправляет **один** multipart-запрос из трёх частей, в указанном порядке:

1. JSON `Photo/LocalAddToAlbum` с теми же числовыми полями, что и у фото.
2. MP4, `name="file"`, `filename="vi-<24 hex>.mp4"`.
3. Обложка WebP, `name="file"`, `filename="vi-<те же 24 hex>.webp"`.

Различия в JSON:

```json
{
  "FileName": "vi-0123456789abcdef01234567.mp4",
  "PreviewFileName": "vi-0123456789abcdef01234567.webp"
}
```

Это только изменённые поля, не полная команда. Хеш в имени вычисляется от **подготовленного MP4**; длина имени MP4 — 31 ASCII-байт, обложки — 32. У обеих файловых частей `Content-Type: application/octet-stream` и собственный `Content-Length`. Прошивка определяет видео по расширению `.mp4`, регистрирует одну запись с `pic_video_flag=1` и перемещает обложку рядом с MP4, заменяя расширение на `.webp`. Обложка не должна импортироваться отдельной командой как фотография.

Параметры подготовки Divoom Times Frame Sync:

| Параметр | Значение |
| --- | --- |
| Контейнер | MP4, `+faststart` |
| Видео | H.264, профиль Main, level 4.0, `yuv420p`, 30 кадров/с |
| Размер | 800×1280; поворот по метаданным, `IMAGE_FIT=contain/cover` |
| Качество | `libx264`, CRF 23, preset medium, maxrate 4 Мбит/с, bufsize 8 Мбит |
| Звук | Первая аудиодорожка, если есть: AAC, 128 кбит/с, stereo, 48 кГц |
| Обложка | Первый кадр подготовленного видео → PNG в памяти → RGB WebP, quality 90, method 4 |
| Длительность | Без ограничения по времени; после обработки сравнивается с исходником, допуск max(0,5 с; 1%) |

FFmpeg и ffprobe запускаются локально; команда подготовки ограничена одним часом, чтение метаданных и создание обложки — 90 секундами каждое. Ошибка завершает текущую синхронизацию до исключения старых записей. Описание флагов: [FFmpeg](https://ffmpeg.org/ffmpeg.html).

Таймаут HTTP для отправки видео: соединение 5 с, ожидание данных ответа 300 с. Это сетевые таймауты, не ограничение длительности ролика. После ACK действуют те же опрос базы и проверка членства. Дополнительно обязательны `pic_video_flag=1`, совпадение SHA-256 MP4 и отдельное совпадение SHA-256 обложки. Проверка файлов читает ответ частями; в памяти целый MP4 не хранится.

Следующий цикл использует сохранённые контрольные суммы, чтобы повторно найти видео и проверить его без скачивания из источника и без FFmpeg. Автозапуск видео, mute и громкость остаются настройками рамки. Сервис не меняет их при импорте.

## 4. `Photo/DevicePhotoToAlbum`

**HTTP:** `POST /upload`, только JSON-часть. **Использование:** `Frame.add_existing()` для существующей фотографии, которой нет в нужном альбоме.

```json
{
  "Command": "Photo/DevicePhotoToAlbum",
  "ReturnCode": 0,
  "ToClockId": 123456,
  "ParentClockId": 0,
  "ParentItemId": 0,
  "PhotoList": [42]
}
```

| Поле | Тип | Значение |
| --- | --- | --- |
| `ToClockId` | integer | ID целевого альбома; здесь именно `ToClockId`, не `ClockId` |
| `ParentClockId`, `ParentItemId` | integer | `0` |
| `PhotoList` | array of integer | ID записей `pic_info`, а не ID исходного сервиса и не имена файлов; текущий клиент передаёт один ID |

Команда добавляет связь уже существующей фотографии с альбомом. Файл повторно не передаётся. Другие связи этой фотографии сохраняются.

После ACK `wait_members()` читает базу до появления всех требуемых ID в целевом альбоме, с теми же 15 с и паузой 0,5 с. Синхронизатор проверяет членство до отправки, поэтому при повторном цикле уже существующая связь не добавляется повторно. Слепое многократное выполнение команды без чтения базы не используется.

## 5. `Photo/RemovePhotoFromAlbum`

**HTTP:** `POST /upload`, только JSON-часть. **Использование:** `Frame.remove_from_album()` в режиме `mirror`.

```json
{
  "Command": "Photo/RemovePhotoFromAlbum",
  "ReturnCode": 0,
  "ClockId": 123456,
  "ParentClockId": 0,
  "ParentItemId": 0,
  "PhotoList": [42, 43]
}
```

| Поле | Тип | Значение |
| --- | --- | --- |
| `ClockId` | integer | ID альбома, из которого нужно исключить фотографии |
| `ParentClockId`, `ParentItemId` | integer | `0` |
| `PhotoList` | array of integer | Отсортированные ID фотографий из базы рамки |

Команда исключает фотографии из указанного альбома. Она не используется для глобального удаления файла: запись `pic_info`, «Все фото» и связи с другими альбомами сохраняются. Пустой набор ID клиент не отправляет. Синхронизатор делит большие удаления на пачки по 100 ID; это ограничение клиента, предел прошивки не установлен.

После ACK `wait_members()` требует отсутствия всех удаляемых ID в `album_pic` для данного альбома. Наличие файла после операции ожидаемо и не считается ошибкой. Если подтверждение не получено, цикл завершается ошибкой и журнал владения сохраняется для следующей попытки.

Перед удалением синхронизатор проверяет, что запись отслеживается в `device-state.json` для того же устройства, целевого альбома и области синхронизации; ID и путь записи всё ещё совпадают; фотография присутствует в целевом альбоме, но не входит в текущий объединённый набор подготовленных изображений. Полный алгоритм и переключение режимов: [sync-modes.md](sync-modes.md).

## 6. `Device/ExitCustomControlMode`

**HTTP:** `POST /divoom_api`. **Использование:** `Frame.restore()`, перед включением штатного альбома и при команде CLI `restore`.

```json
{"Command": "Device/ExitCustomControlMode", "ReturnCode": 0}
```

Дополнительных параметров нет. Команда выводит устройство из режима внешнего управления экраном, который использовался старым экспериментальным способом показа. Она не загружает и не удаляет фотографии и сама по себе не выбирает нужный альбом.

Ответ проверяется через `_post()`. При включении альбома далее следует `Channel/SetClockSelectId`. При CLI `restore` выбирается сохранённый `previous_clock_id`, если он есть. Отдельной проверки режима custom control после выхода клиент не делает; итоговая проверка при `play_album()` относится к выбранному `ClockId`.

## 7. `Channel/SetClockSelectId`

**HTTP:** `POST /divoom_api`. **Использование:** `Frame.select_clock()` для выбора альбома и восстановления предыдущего экрана.

```json
{"Command": "Channel/SetClockSelectId", "ReturnCode": 0, "ClockId": 123456}
```

`ClockId` — integer, ID существующего альбома или циферблата. Перед выбором целевого альбома его ID находится по точному имени `DIVOOM_ALBUM` в базе. Должен существовать ровно один обычный альбом с таким именем.

На исследованной прошивке два последовательных вызова позволяли преодолеть текущий запланированный циферблат. Поэтому `select_clock()` отправляет команду дважды и проверяет оба ACK. Дальнейшее расписание и стартовый экран при перезагрузке рамки программа не перенастраивает.

`play_album()` затем вызывает `Channel/GetClockInfo` и сравнивает `ClockId`. CLI `restore` использует только `select_clock()` и не делает эту дополнительную проверку. Повторный выбор может повлиять на показ, поэтому `run` выбирает альбом только при первом успешном непустом цикле, а не при каждой проверке источников.

## 8. `Device/GetScreenSnapshot`

**HTTP:** `POST /divoom_api`. **Использование:** `Frame.snapshot()`, команда CLI `snapshot`.

```json
{"Command": "Device/GetScreenSnapshot", "ReturnCode": 0}
```

Сокращённый ответ исследованного устройства:

```json
{
  "Command": "Device/GetScreenSnapshot",
  "ReturnCode": 0,
  "snapShotPath": "/userdata/app_pic/snapshot.webp"
}
```

Обратите внимание на регистр `snapShotPath`. Команда создаёт файл на устройстве; байты изображения не входят в JSON-ответ. Клиент ждёт 2 с, затем скачивает файл по этому пути. Если поле отсутствует, код использует резервный путь `/userdata/snapshot.webp`.

Файл должен находиться внутри `/userdata/`. HTTP 404 при скачивании превращается в ошибку «snapshot file not found». CLI сохраняет полученные байты атомарно в `DATA_DIR/snapshot.webp`. Команда не переключает фотографию. Последующие снимки могут перезаписывать тот же файл на рамке и на компьютере; отдельный идентификатор или проверка свежести снимка в текущем клиенте отсутствуют.

## 9. `GET /userdata/pic_db.bin`

**HTTP:** GET без JSON. **Использование:** `Frame.inventory()`; обнаружение альбома, переиспользование файлов и подтверждение изменений.

HTTP 200 должен содержать бинарную SQLite-базу. Клиент десериализует её в `:memory:`, включает `PRAGMA query_only=ON`, требует `PRAGMA quick_check == "ok"` и выполняет запросы:

```sql
SELECT * FROM album_head;
SELECT id, path_name FROM pic_info;
SELECT album_id, pic_id FROM album_pic;
```

Используемые данные:

| Таблица | Интерпретация |
| --- | --- |
| `album_head` | Первые три столбца исследованной схемы: ID, тип, имя. Тип `0` — обычный альбом; тип `1` встречался у «Все фото» |
| `pic_info` | `id` — ID фото для `PhotoList`; `path_name` — абсолютный путь к файлу; `pic_video_flag=1` — видео |
| `album_pic` | Пары `album_id`, `pic_id`, определяющие членство |

Результат — `Inventory(albums, photos, members, video_ids)`. `photos` содержит все медиа, `video_ids` — отдельное множество видео. На старой схеме без `pic_video_flag` фотографии доступны, а видео не пройдут обязательную проверку типа. Альбом выбирается по точному имени, с учётом регистра, только среди типа `0`. Отсутствие или два совпадения дают ошибку; программа не создаёт альбом автоматически и не выбирает другой вместо него.

При ошибке разбора/`quick_check` чтение повторяется до трёх раз с паузой 0,5 с. HTTP 404 означает недоступность нужного интерфейса прошивки и сразу даёт ошибку. Сетевая ошибка также передаётся вызывающему коду.

Скачивание работающей базы не является SQLite backup-транзакцией; проверка целостности выявляет повреждённый снимок, но не фиксирует состояние рамки на всё время синхронизации. Поэтому после изменений выполняются новые чтения. Ни база, ни её отредактированная копия обратно на устройство не записываются.

## 10. `GET /userdata/<path>`

**HTTP:** GET без JSON. **Использование:** `Frame.fetch_file()` для базы, готовых фотографий и снимка экрана; `Frame.file_digest()` для проверки MP4 и их обложек.

Пример пути готовой фотографии:

```text
/userdata/app_pic/20269/im-0123456789abcdef01234567.webp
```

Путь принимается из базы или ответа `Device/GetScreenSnapshot`. Метод разрешает только строки, начинающиеся с `/userdata/`, и отвергает компонент `..`. Ответ HTTP 200 возвращается как `bytes`; 404 возвращает `None`; другие неуспешные статусы и сетевые ошибки дают `SyncError`.

Для фотографий проверяется SHA-256 прочитанных байтов: он должен совпасть с сохранённой контрольной суммой WebP или результатом текущего `device_photo()`. Несовпадение существующего файла останавливает синхронизацию: клиент не перезаписывает его и не создаёт ещё одну запись с тем же именем. Для снимка экрана достаточно успешного скачивания.

`file_digest()` разрешает те же пути и возвращает hex SHA-256 или `None` для 404. Он использует `stream=True`, читает ответ по 1 МиБ; таймаут соединения 5 с, чтения — 90 с. Обрыв, ошибка HTTP или несовпадение контрольной суммы оставляют подготовленный локальный файл для следующей попытки и блокируют исключение старых записей. Обложка видео читается по пути MP4 с расширением `.webp`.

## Последовательность одного цикла

1. Проверить доступность API рамки; если она недоступна, пропустить цикл без изменения локальных манифестов. Прочитать полные списки всех исходных альбомов соответствующей цели и сохранить манифесты. Ошибка на этом этапе пропускает целевой альбом до команд изменения рамки; независимые цели могут обновиться.
2. Прочитать базу рамки, найти альбом по имени, получить `Channel/GetConfig` и `Channel/GetClockInfo`.
3. Для каждого фото и видео найти запись по основному имени или имени восстановленной копии. Использовать сохранённую проверку только при совпадении области журнала, ID, пути, типа, полного хеша файла и обложки; иначе прочитать содержимое и сверить SHA-256. Для нового или отсутствующего фото подготовить временный JPEG и WebP; для видео — MP4 с обложкой; выполнить `Photo/LocalAddToAlbum` / `Photo/DevicePhotoToAlbum` при необходимости.
4. После каждого подтверждённого элемента сохранить запись в журнале и удалить временный JPEG либо MP4 с обложкой. Перед исключением исчезнувших записей снова прочитать базу и проверить ID целевого альбома.
5. В режиме `mirror` исключить отслеживаемые исчезнувшие изображения через `Photo/RemovePhotoFromAlbum`. В `append` сохранить их и сведения о них.
6. Проверить членство текущих изображений, сохранить журнал. При необходимости включить альбом через выход из custom control и выбор `ClockId`.

`sync --dry-run` выполняет чтение статуса, а не расчёт списка будущих удалений. `snapshot` и `restore` — отдельные диагностические/управляющие команды. Неиспользуемые экспериментальные команды и доступ к бинарнику прошивки не нужны при обычной работе.

## Операции восстановления

`repair` использует перечисленные выше GET и native-команды Photo. Он читает текущие настроенные медиа целиком и сверяет SHA-256; для видео также нужны правильная обложка и `pic_video_flag=1`. `repair --dry-run` выполняет эти чтения без команд изменения рамки. HTTP 404 и завершённая проверка с несовпадением хеша допускают восстановление; сетевые ошибки и другие ошибки HTTP не считаются доказательством повреждения.

Повреждённый файл заменяется отдельной копией с именем `r<24 hex SHA-256 содержимого><2 hex поколения>.webp` либо `.mp4` через `Photo/LocalAddToAlbum`. Поколения начинаются с `00`; имя WebP занимает 32 байта, MP4 — 31. `Inventory.find_media()` выбирает наибольшее поколение, в том числе после потери журнала, но доверие записывается только после полной проверки хеша. Исчерпание поколений вызывает ошибку, а не перезапись существующего имени.

После одной проверки новой копии `Photo/DevicePhotoToAlbum` восстанавливает её связи во всех затронутых обычных альбомах. Затем `Photo/RemovePhotoFromAlbum` исключает повреждённые записи. После изменений база читается повторно. Незавершённая операция хранится в журнале и возобновляется при повторном `repair`. Синхронизатор не вызывает глобальное удаление и не редактирует SQLite: старые повреждённые файлы остаются во «Все фото». Показ не переключается. [Подробности repair](repair.md).

`import_photo()` / `import_video()` по умолчанию проверяют содержимое. Синхронизатор передаёт `verify=False`, чтобы выполнить единственную проверку при сверке; импорт всё равно ожидает появления записи в базе и связи с альбомом. Это устраняет двойное чтение новой загрузки.
