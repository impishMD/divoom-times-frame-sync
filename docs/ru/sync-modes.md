# Режимы синхронизации альбома

[English](../en/sync-modes.md) | **Русский**

Режим выбирается для команд `sync` и `run`. Он определяет, что делать с ранее отслеживаемыми фотографиями, которых больше нет в исходном альбоме или объединении источников целевого альбома. Способ хранения и автономного показа на рамке в обоих режимах одинаков.

Эти правила одинаково применяются к фотографиям и видео. Видео загружаются из Google Photos, iCloud Photos, Immich, OneDrive и Яндекс Диска; тип записи не меняет правил владения, исключения из альбома и восстановления после перезапуска.

## Выбор режима

| Режим | Новые фото | Исчезнувшие фото | Старая версия изменённого фото |
| --- | --- | --- | --- |
| `mirror` | Добавить | Исключить из целевого альбома | Исключить после подтверждения новой версии |
| `append` | Добавить | Оставить | Оставить рядом с новой версией |

По умолчанию — `mirror`. Приоритет настроек:

1. `--sync-mode` в командной строке.
2. `SYNC_MODE` в окружении процесса.
3. `SYNC_MODE` из `.env` или файла, выбранного через `--env-file`.
4. Значение по умолчанию `mirror`.

Неизвестное значение даёт ошибку до выполнения синхронизации.

Разовая синхронизация с удалением исчезнувших фотографий:

```sh
.venv/bin/tfs sync --sync-mode mirror
```

Постоянная синхронизация в том же режиме:

```sh
.venv/bin/tfs run --sync-mode mirror
```

Только добавлять фотографии:

```sh
.venv/bin/tfs run --sync-mode append
```

Постоянная настройка в `.env`, в том числе для Docker Compose:

```dotenv
SYNC_MODE=mirror
SYNC_INTERVAL=300
```

После изменения `.env` перезапустите работающий процесс: настройки читаются при старте. Для уже созданного контейнера используйте `docker compose up -d --no-build --force-recreate`. Для сборки обновлённых локальных исходников используйте `docker compose up -d --build --pull never`.

## Что означает удаление в `mirror`

Пример: Immich содержит A и B, а в целевом альбоме рамки есть загруженные сервисом A, B и вручную добавленная C. После исключения A из Immich следующий успешный цикл оставляет в целевом альбоме B и C. Для удаления достаточно убрать фото из исходного альбома; удалять оригинал из библиотеки Immich не требуется.

Применяется `Photo/RemovePhotoFromAlbum`: исключается связь фотографии с **целевым альбомом**. Файл остаётся в памяти рамки и может по-прежнему быть виден в «Все фото» или других альбомах. Это не очистка свободного места и не глобальное удаление через `Photo/DeletePhoto`.

Сервис удаляет только свои отслеживаемые записи. Перед удалением должны одновременно выполняться условия:

- В `device-state.json` совпадают устройство (`DeviceId`), ID целевого альбома и ID исходного альбома (для старой одиночной конфигурации) или стабильный ID группы назначения (для списка источников). Журнал также привязан к адресу и порту рамки.
- Запись известна локальному журналу: была импортирована или переиспользована после проверки её байтов.
- В свежей базе рамки ID и путь фотографии совпадают с записью журнала. Это защищает от удаления постороннего файла при повторном использовании числового ID.
- Фото ещё находится в целевом альбоме, но не входит в текущий объединённый набор подготовленных изображений.

Если два исходных фото дают одинаковые подготовленные WebP-байты, они представлены одной записью рамки. Она сохраняется, пока хотя бы одно из этих изображений остаётся хотя бы в одном источнике.

## Пустой альбом и ошибки

Успешно прочитанный **пустой** альбом является корректным состоянием. В `mirror` все отслеживаемые фото исключаются из целевого альбома; ручные фото остаются. В `append` фотографии и записи журнала сохраняются. При пустом наборе программа не переключает активный экран; вид пустого альбома определяется прошивкой.

Ошибка доступа к исходному сервису не равна пустому альбому. Сначала читается полный список и проверяются количества элементов. Превью скачиваются по одному только при необходимости загрузки на рамку. Если список получить не удалось, CLI не вызывает обновление рамки по старому манифесту. В штатном цикле удаления начинаются только после подтверждения всех текущих фотографий на рамке.

Изменения на рамке не являются общей транзакцией. Если несколько новых фото уже добавились, а следующая загрузка завершилась ошибкой, добавленные могут остаться, но удаление старых ещё не начинается. Если ошибка произошла при удалении одной из пачек, предыдущие пачки уже могли выполниться. Журнал сохраняет сведения для повторного цикла; программа заново читает базу и продолжает по фактическому состоянию.

Если несколько источников направлены в один альбом, ошибка чтения списка любого из них блокирует обновление всей этой цели до начала загрузок. Остальные целевые альбомы продолжают синхронизацию. Успешно прочитанный пустой источник убирается из объединения, но фото других источников остаются.

## Переключение между режимами

В `append` сервис продолжает учитывать оставленные фотографии в журнале. После перехода на `mirror` они будут исключены, если к этому времени всё ещё отсутствуют в источниках. Это работает и после перезапуска программы, и после нескольких циклов с пустым исходным альбомом.

В старой одиночной конфигурации смена устройства, исходного или целевого альбома меняет область журнала. В конфигурации `SOURCES_FILE` отдельный журнал хранится для каждого целевого альбома; изменение его состава источников меняет объединённый набор. Удаление секции источника в `mirror` может исключить его фото из общей цели; исчезнувшая из конфигурации целиком цель больше не обновляется. Полные правила — [sources.md](sources.md).

Если журнал (`data/device-state.json` в старой конфигурации или `data/targets/<hash>/device-state.json` для списка источников) утрачен, текущие изображения можно найти на рамке по именам и подтвердить по байтам. Для уже исчезнувших из источников фото восстановить владение таким способом нельзя: сервис не удаляет их только по префиксу имени. Сохраняйте журнал между запусками и подключайте постоянный `./data:/app/data` в контейнере.

## Проверка работы

`status` показывает режим из конфигурации и число фотографий и видео в целевом альбоме, включая ручные. `sync --sync-mode mirror --dry-run` показывает статус с учётом выбранного режима, без записи на рамку. Это не список будущих удалений.

По умолчанию уровень `INFO` показывает запуск и остановку сервиса, а также одну сводку после первого успешного цикла или цикла с загрузками, восстановлением состава альбома либо удалениями:

```text
INFO Service started; sync interval=30s
INFO Sync cycle complete: 87 items, 1 uploaded, 0 removed; 9.0s
```

Неизменившиеся циклы не засоряют лог. В режиме `run` сводка повторяется, когда с последней INFO-сводки прошло не менее 10 минут: её выводит следующий успешный цикл. Разовый `sync` всегда сообщает результат. Предупреждения, ошибки и обнаруженные повреждения остаются видны сразу. Неудачные циклы, включая частичные ошибки, не выводят сообщение об успешной работе.

Перед чтением альбомов источников `sync` и каждый цикл `run` отправляют на рамку запрос `Channel/GetClockInfo`, который только читает состояние, с таймаутами соединения/чтения по 3 секунды. При сетевой ошибке или таймауте цикл пропускается: источники не опрашиваются, медиа не скачиваются, локальные списки и журналы остаются прежними. `run` повторяет проверку после `SYNC_INTERVAL` и продолжает работу после восстановления связи. Команда `cache` по-прежнему работает независимо от рамки.

При потере связи сразу появляется одно предупреждение, затем оно повторяется не чаще раза в 10 минут, пока рамка недоступна. Остальные пропущенные циклы и времена вложенных операций видны только в DEBUG. Когда цикл проходит без сетевой ошибки рамки, сервис сообщает о восстановлении связи и результате цикла. Отказ API, ошибка HTTP или некорректный JSON остаются ошибками, а не пропуском из-за недоступности. Разовый `sync` при недоступной рамке возвращает ненулевой код завершения.

```text
WARNING Frame unavailable; sync cycle skipped; retry in 30s; 3.0s
INFO Frame connection restored after 126.0s; resuming sync
INFO Sync cycle complete: 87 items, 0 uploaded, 0 removed; 2.0s
```

Если связь пропадает после проверки, текущий цикл прерывается, остальные цели не обрабатываются. Уже выполненные изменения сохраняются в журналах. К текущему запросу применяются обычные таймауты передачи: начальная проверка не гарантирует доступность рамки на протяжении последующей загрузки. Сам факт недоступности рамки не приводит к удалениям; пропущенный цикл не считается успешным.

`items` — число текущих исходных медиа суммарно по завершённым целям: один файл в двух целевых альбомах учитывается дважды. `uploaded` и `removed` — изменения за этот цикл. Ненулевой счётчик `linked` означает, что уже имеющиеся на рамке медиа добавлены обратно в целевой альбом без повторной загрузки. Для счётчиков каждой цели и всех таймеров включите DEBUG:

```sh
.venv/bin/tfs --log-level DEBUG run
```

Пример подробного лога завершённого цикла:

```text
DEBUG Source family (immich), album Family: listed 2 photos, 1 videos; 0 prefetched, 0 videos skipped; 0.5s
DEBUG Native album Photos (123456), mode=mirror: 2 photos, 1 videos, 3 matched metadata, 0 content checked, 0 downloaded, 0 uploaded, 0 linked, 1 removed, 0 missing items retained; 1.2s
INFO Sync cycle complete: 3 items, 0 uploaded, 1 removed; 1.8s
```

На уровне DEBUG разовый `sync` и каждый цикл `run` показывают три длительности, измеренные монотонными часами:

- `Source` (или `Immich album` в одиночном режиме): получение полного списка одного исходного альбома и обновление его локального манифеста. При явном запуске `cache` сюда также входит предварительное скачивание.
- `Native album`: синхронизация одной цели, включая чтение базы рамки, сверку, необходимые скачивания из источников и конвертацию, загрузки, проверки, запись журнала и выбор альбома для показа, если он запрошен. Получение списка источника сюда не входит; это не время одного HTTP-запроса.
- `Sync cycle`: вся операция по всем настроенным источникам и целям, включая проверку доступности рамки и подготовку между этапами. Получение блокировки и пауза `SYNC_INTERVAL` не учитываются; пауза начинается после этой строки.

Общее время может немного отличаться от суммы показанных этапов из-за промежуточных операций и округления. При частичной ошибке выводится `Sync cycle finished with N errors`, при исключении, остановившем цикл, — `Sync cycle failed`; обе строки содержат длительность.

Отдельные операции показывают длительность на уровне DEBUG. Например, для новой фотографии:

```text
Downloading photo: complete; 0.4s
Preparing photo: complete; 0.2s
Uploading native photo: complete; 1.3s
Checking photo contents in album Photos: complete; 0.7s
Removing temporary photo files: complete; 0.0s
```

Для видео отдельно измеряются скачивание, конвертация MP4, создание обложки, локальные контрольные суммы, загрузка и проверка видео с обложкой. Время также показывают изменения состава альбома, выбор показа, операции и итоги repair, подготовка кэша, чтение статуса, получение скриншота и возврат прежнего экрана. Измеряется вся операция, включая необходимые ожидания и повторы; время вложенного этапа не нужно прибавлять к длительности родительского.

`complete` выводится после завершения операции. Долгие видеооперации сначала сообщают `started; 0.0s elapsed`, а затем — итоговое время; промежуточная строка чтения с рамки показывает количество МиБ и прошедшее время. `failed`, `interrupted` и `problems found` различают ошибку, прерывание и завершённую проверку с обнаруженным повреждением. Секунды округляются до одного знака: очень короткая операция может показывать `0.0s`. Для повторно используемых медиа дополнительные проверки и загрузки ради логирования не выполняются.

DEBUG также показывает время API-вызовов рамки, чтения базы, ожиданий импорта и состава альбома, локальных манифестов, записи журнала и обслуживания временных файлов. Успешные операции с отдельными файлами и подробности источников и целей остаются в DEBUG даже при наличии изменений. Явные команды `repair`, `cache`, `status`, `snapshot` и `restore` сохраняют итоговые сообщения в INFO. DEBUG включается только для логов приложения; отладочные логи HTTP-библиотек, в которых могут быть приватные URL, остаются выключенными.

`photos` и `videos` — число уникальных подготовленных фото и видео текущего объединения источников; `removed` — число записей, исключённых из целевого альбома; `missing items retained` — число отслеживаемых записей, оставленных режимом `append`, несмотря на их отсутствие в текущем наборе. Ручные фотографии в эти счётчики не входят.

Подробное описание команды удаления и её проверки: [frame-api.md](frame-api.md).

`matched metadata` — элементы, использованные без чтения медиа; `content checked` — полные проверки содержимого, включая новые загрузки. При первом обновлении существующие файлы проверяются один раз. Полный аудит независимо от mirror/append выполняет [repair](repair.md).
