# Релизы и публикация контейнеров

[English](../en/releases.md) | **Русский**

## Workflow

- **CI** запускается при push в `main`, в pull request, вручную и в составе релиза. Выполняет Python-тесты на 3.11 и 3.13 и собирает контейнеры на нативных раннерах AMD64 и ARM64. Проверки контейнеров охватывают CLI, Python-зависимости, поддержку WebP и короткое преобразование H.264/AAC без сетевого доступа.
- **Packages** запускается при тех же событиях и собирает Python wheel, sdist и полный архив исходников из Git-коммита. Проверяет установку из всех трёх архивов и загружает их вместе с `checksums.txt` как артефакт Actions.
- **Release** запускается при push тега, соответствующего `v[0-9]*`. Вызывает оба workflow, создаёт черновик GitHub Release, собирает и проверяет образы обоих реестров на каждой нативной архитектуре, затем публикует мультиплатформенные теги и релиз. При ошибке релиз остаётся черновиком; теги `latest` обновляются только после проверки манифестов обеих версий в реестрах.

CI и Packages пропускают события push и pull request, если все изменённые файлы находятся в `docs/` или являются Markdown-файлами в корне репозитория. Изменения кода, зависимостей, файлов сборки или workflow запускают оба workflow, в том числе когда тот же коммит обновляет документацию. Ручные запуски и проверки, вызванные Release, выполняются всегда.

Опубликованные контейнеры поддерживают `linux/amd64` и `linux/arm64`:

```text
docker.io/impishmd/divoom-times-frame-sync:v0.5.0
ghcr.io/impishmd/divoom-times-frame-sync:v0.5.0
```

Стабильные версии также обновляют `latest` в обоих реестрах. Предварительные версии его не меняют. Версия сервиса задаётся в `pyproject.toml`; теги контейнеров добавляют префикс `v`. Изменяемые алиасы major/minor не создаются. Релизы выполняются последовательно, чтобы не обновлять `latest` одновременно. Не публикуйте старую стабильную версию после новой, если не хотите откатить `latest`.

## Настройка репозитория

1. Включите GitHub Actions и разрешите actions, указанные в workflow.
2. Создайте GitHub environment **`docker_hub`** с двумя **секретами**:
   - `DOCKERHUB_USR`: логин Docker Hub с правом push в `impishmd/divoom-times-frame-sync`.
   - `DOCKERHUB_TOKEN`: токен Docker Hub с правами чтения и записи в этот репозиторий.
3. Если environment ограничивает ветки или теги развёртывания, разрешите релизные теги. Настроенные подтверждения environment применяются к заданиям публикации образов.
4. GHCR использует `GITHUB_TOKEN` workflow с правом `packages: write`; отдельный токен не нужен. Если пакет уже существует, предоставьте этому репозиторию доступ Actions к пакету. OCI-метка исходников связывает образ с репозиторием.

Видимость репозитория и пакета настраивается отдельно. Новый пакет GHCR по умолчанию приватный; для анонимного скачивания переключите его видимость на публичную. Видимость репозитория Docker Hub настраивается независимо. Workflow не меняет эти настройки.

## Выпуск версии

1. Обновите `project.version` в `pyproject.toml`.
2. Добавьте английские заметки о релизе в `docs/en/releases/v<VERSION>.md` и русский перевод в `docs/ru/releases/v<VERSION>.md`. При необходимости обновите примеры версий в обоих README. GitHub Release использует английский текст. В заметках используйте абсолютные ссылки на файлы репозитория, чтобы они работали и на странице релиза GitHub.
3. Создайте коммит, отправьте его в `main` и дождитесь успешных CI и Packages.
4. Создайте и отправьте аннотированный тег, совпадающий с версией пакета:

   ```sh
   git tag -a v0.5.0 -m 'v0.5.0'
   git push origin v0.5.0
   ```

Используйте версии, совместимые с Python: `0.5.0` для стабильного релиза либо `0.6.0rc1`, `0.6.0a1`, `0.6.0b1` для предварительных. Соответствующие теги — `v0.5.0`, `v0.6.0rc1` и т. д. Некорректный тег, несовпадение версии, отсутствие или пустое содержимое заметок о релизе останавливают pipeline до публикации.

Опубликованные релизы не перезаписываются. При временной ошибке реестра перезапустите упавшие задания того же запуска Actions. Если после публикации нужны изменения исходников или workflow, создайте новую версию вместо перемещения тега. При недоступности реестра один тег версии или алиас `latest` может обновиться раньше другого; повторный запуск задания публикации завершит оба обновления. Публикация в два реестра не является атомарной.

## Артефакты релиза и проверка

Каждый GitHub Release включает:

- `divoom-times-frame-sync-v<VERSION>-source.tar.gz`: полное дерево отслеживаемых исходников, включая workflow и документацию, без истории Git.
- `timesframesync-<VERSION>.tar.gz`: исходный Python-дистрибутив.
- `timesframesync-<VERSION>-py3-none-any.whl`: Python wheel.
- `checksums.txt`: SHA-256 трёх архивов.
- `container-digests.txt`: неизменяемые ссылки на манифесты образов обоих реестров.

GitHub также автоматически предоставляет исходники в ZIP и tar.gz. Wheel и sdist сохраняют имя Python-дистрибутива `timesframesync`; команда CLI — `tfs`.

```sh
sha256sum -c checksums.txt
docker buildx imagetools inspect impishmd/divoom-times-frame-sync:v0.5.0
docker buildx imagetools inspect ghcr.io/impishmd/divoom-times-frame-sync:v0.5.0
```

На macOS используйте `shasum -a 256 -c checksums.txt`. Для просмотра или скачивания приватного образа сначала войдите в реестр. Сводка Actions и `container-digests.txt` указывают точные манифесты образов; ссылка `image@sha256:...` позволяет закрепить развёртывание на неизменяемом образе.
