# Штатный фотоальбом Times Frame: LAN-протокол

Описание составлено по поведению прошивки Times Frame от сентября 2026 года. Использованы HTTP-запросы к устройству, чтение его базы и статический разбор собственной программы рамки. USB и облачная авторизация Divoom не требуются.

Подробный справочник всех используемых запросов: [frame-api.md](frame-api.md). Выбор политики удаления: [sync-modes.md](sync-modes.md).

## Подтверждённые операции

Обычные команды управления экраном принимаются через `POST /divoom_api`. Но `Photo/*` на исследованной прошивке могут вернуть `ReturnCode: 0` без выполнения. Рабочая точка для них — **`POST /upload`**, которая передаёт JSON в общую очередь native-команд.

Запрос — multipart/form-data. Первая часть: JSON, `name="json"`, `filename="cmd.json"`, `Content-Type: application/json`. Для каждой части обязателен собственный `Content-Length`, разделители строк CRLF. Вторая часть при импорте содержит изображение. Для изменения состава альбома достаточно одной JSON-части.

Общие поля JSON:

```json
{
  "Command": "Photo/LocalAddToAlbum",
  "ReturnCode": 0,
  "DeviceToken": 123456,
  "LocalToken": 123456
}
```

`ReturnCode: 0` здесь является частью входного сообщения, которое разбирает общий обработчик прошивки; одного HTTP-ответа с таким кодом недостаточно для проверки результата.

## Импорт фотографии

Дополнительные поля:

| Поле | Значение |
| --- | --- |
| `ClockId` | ID существующего штатного альбома |
| `ParentClockId`, `ParentItemId` | 0 для обычного альбома |
| `UserId` | Числовой ID отправителя |
| `SendTime`, `TakingTime` | Unix time в миллисекундах |
| `PhotoX`, `PhotoY` | 0 |
| `PhotoWidth`, `PhotoHeight` | 800, 1280 |
| `PhotoIndex`, `PhotoTotalCnt` | 0, 1 — каждый файл отдельной операцией |
| `PhotoFlag` | Числовой идентификатор партии |
| `FileName` | Короткое имя файла, совпадающее с именем второй multipart-части |
| `PreviewFileName`, `PhotoTitle` | Пустые строки |

Загрузчик сначала сохраняет `/userdata/app_pic/<FileName>`. Затем `Photo/LocalAddToAlbum` перемещает его в `/userdata/app_pic/<год><месяц>/<FileName>`, регистрирует в `pic_info` и связывает с альбомом через `album_pic`. Месяц в наблюдавшихся путях не дополнен нулём: например, `20269`.

Используются одиночные WebP и имена `im-<24 hex символа SHA-256>.webp` длиной 32 байта. **Не использовать длинные имена или пути вместо имени файла.** В прошивке обнаружен 128-байтный буфер команды копирования обложки. Длинное имя с UUID приводило к перезапуску приложения рамки после регистрации изображения, до добавления в альбом. Короткие имена устранили сбой.

Проверка импорта:

1. Получить свежую копию `GET /userdata/pic_db.bin`.
2. Проверить SQLite `quick_check`; найти фото по короткому имени в `pic_info.path_name`.
3. Проверить наличие пары `album_id`, `pic_id` в `album_pic`.
4. Скачать фото по найденному пути и сравнить байты с отправленными.

Программа читает SQLite только в памяти. База на устройстве не редактируется и обратно не загружается.

## Импорт видео

Используется тот же `Photo/LocalAddToAlbum`, но в одном multipart передаются JSON, MP4 и WebP-обложка. Имена частей файлов — `file`. Поле `FileName` содержит `vi-<24 hex SHA-256 MP4>.mp4`, `PreviewFileName` — тот же stem с `.webp`. Остальные поля совпадают с импортом фото, включая размеры 800×1280.

Прошивка определяет `.mp4` как видео (`pic_info.pic_video_flag=1`), переносит файл и обложку в датированный каталог. Обложка лежит рядом с MP4 и не образует отдельную запись фотографии. Проверяются оба SHA-256, флаг видео и членство в альбоме. Подробности кодирования и сетевого транспорта — [справочник API](frame-api.md#импорт-видео-той-же-командой).

В изученном бинарнике декодер читает `PreviewFileName` в поле структуры со смещением `0xb8`, а `FileName` — `0x38`. В импортёре `0xff27c` отдельная непустая обложка перемещается к ролику; обработчик `0x184e10` устанавливает флаг видео при расширении `.mp4`. Эти детали описывают изученную прошивку и не считаются стабильным публичным контрактом Divoom.

## Состав альбома и показ

Добавить уже зарегистрированное изображение:

```json
{
  "Command": "Photo/DevicePhotoToAlbum", "ReturnCode": 0,
  "ToClockId": 123456, "ParentClockId": 0, "ParentItemId": 0,
  "PhotoList": [42]
}
```

Исключить изображение из конкретного альбома:

```json
{
  "Command": "Photo/RemovePhotoFromAlbum", "ReturnCode": 0,
  "ClockId": 123456, "ParentClockId": 0, "ParentItemId": 0,
  "PhotoList": [42]
}
```

Обе команды передаются JSON-only multipart через `/upload`. Их действие проверяется чтением базы. Синхронизатор не использует глобальное `Photo/DeletePhoto`: исключённые копии могут быть нужны другим альбомам.

Для включения альбома: `Device/ExitCustomControlMode`, затем два вызова `Channel/SetClockSelectId` с `ClockId` альбома через `/divoom_api`. Двойной выбор на этой прошивке подавляет текущий запланированный циферблат. Проверка — `Channel/GetClockInfo.ClockId`.

Интервал и эффекты остаются штатными настройками Divoom. `Photo/SetAlbumConfig.SlideshowSpeed` — не секунды: обработчик преобразует шкалу 0–100 примерно в 20–3 секунды. Поэтому старый `SLIDE_INTERVAL=30` из экспериментального режима сюда не переносится.

## Воспроизводимость исследования

Исследованный ELF `/usr/bin/divoom_app`, SHA-256:

```text
d8eb027cfc0c4b3f6413497dda1d62926a1bfe86861990841298f33ebdaf7de2
```

Полезные адреса в ARM32-бинарнике: декодер `Photo/LocalAddToAlbum` — `0x1a4b28`, импорт — `0xff27c`, обработчик `/upload` — `0x23a3e4`, изменение состава альбома — `0xd3520`, формирование команды копирования обложки — `0x106940`.

Бинарник прошивки, базы устройства и фотографии не включаются в репозиторий и не являются зависимостями Divoom Times Frame Sync.
